# Руководство по разработке системы ведения протоколов совещаний

## 1. Назначение документа

Настоящий документ устанавливает обязательные правила и рекомендуемые практики разработки системы ведения протоколов совещаний.

Архитектура проекта:

- фронтенд: одностраничное приложение на HTML, CSS и JavaScript без серверного рендеринга;
- бэкенд: TypeScript в среде Node.js;
- база данных: PostgreSQL;
- взаимодействие фронтенда и бэкенда: REST API по HTTP/HTTPS;
- фронтенд, бэкенд и PostgreSQL запускаются в отдельных контейнерах;
- совместный запуск локального окружения выполняется через Docker Compose.

Документ обязателен для разработчиков, выполняющих изменение исходного кода, структуры базы данных, REST API, контейнеров и конфигурации проекта.

---

## 2. Общие принципы разработки

- Код должен быть понятным без необходимости восстанавливать замысел автора.
- Одна функция должна выполнять одну логически завершённую операцию.
- Дублирование кода следует устранять через функции, модули или общие утилиты.
- Бизнес-правила должны находиться на бэкенде, а не только во фронтенде.
- Фронтенд не должен обращаться к PostgreSQL напрямую.
- Все операции с данными выполняются через REST API.
- База данных является источником истины для совещаний, протоколов, обсуждений, решений, задач и статусов.
- Конфигурация среды не должна быть жёстко записана в исходном коде.
- Секреты, пароли и токены запрещено сохранять в репозитории.
- Любое изменение структуры БД выполняется миграцией.
- Любое изменение публичного REST API должно быть отражено в документации API.
- Код должен проходить форматирование, статический анализ и тесты до включения в основную ветку.

# 3. Соглашения об именовании

## 3.1. Общие требования

Имена должны:

- отражать назначение сущности;
- быть написаны на английском языке;
- не содержать транслитерацию;
- не использовать неочевидные сокращения;
- не содержать тип переменной в имени;
- сохранять единый термин во всех слоях системы.

Пример единой терминологии:

| Понятие | Допустимое имя |
|---|---|
| Совещание | `meeting` |
| Протокол | `protocol` |
| Пункт повестки | `agendaItem` |
| Обсуждение | `discussion` |
| Решение | `decision` |
| Задача | `task` |
| Ответственный | `responsiblePerson` |
| Плановый срок | `plannedDueDate` |
| Фактическая дата завершения | `actualCompletionDate` |

Не следует использовать разные слова для одной сущности, например одновременно `meetingNote`, `minutes` и `protocol`.

## 3.2. Имена каталогов и файлов

Для каталогов и файлов используется `kebab-case`.

```text
meeting-list.js
meeting-form.js
task-status-badge.js
protocol-controller.ts
task-service.ts
database-client.ts
```

Исключения:

- `Dockerfile`;
- `README.md`;
- `LICENSE`;
- `.env`;
- файлы конфигурации, имя которых определяется инструментом;
- файлы миграций, создаваемые выбранным инструментом.

Тестовый файл должен повторять имя тестируемого модуля:

```text
task-service.ts
task-service.test.ts
```

Имена файлов не должны содержать общие слова без контекста:

```text
utils.ts          // нежелательно
helpers.ts        // нежелательно
common.ts         // нежелательно
```

Предпочтительно:

```text
date-format.ts
task-status.ts
http-response.ts
protocol-validation.ts
```

## 3.3. Имена переменных и функций

Для переменных и функций в JavaScript и TypeScript используется `camelCase`.

```ts
const meetingId = request.params.meetingId;
const plannedDueDate = task.plannedDueDate;

function calculateTaskProgress(): number {
  // ...
}
```

Имена функций должны начинаться с глагола:

```ts
getMeetingById()
createProtocol()
updateTaskStatus()
validateDecision()
formatMeetingDate()
```

Для булевых переменных используются префиксы:

- `is`;
- `has`;
- `can`;
- `should`;
- `was`.

```ts
const isCompleted = task.status === 'COMPLETED';
const hasDecisions = discussion.decisions.length > 0;
const canEditProtocol = user.permissions.includes('protocol:update');
```

Массивы и коллекции именуются во множественном числе:

```ts
const meetings = [];
const taskIds = [];
const discussionSpeakers = [];
```

Запрещены однобуквенные имена, кроме локальных индексов короткого цикла и общепринятых координат.

Нежелательно:

```ts
const d = await repository.find(id);
```

Предпочтительно:

```ts
const discussion = await discussionRepository.findById(discussionId);
```

## 3.4. Константы и макросы

В JavaScript и TypeScript для глобальных неизменяемых констант используется `UPPER_SNAKE_CASE`.

```ts
const DEFAULT_PAGE_SIZE = 25;
const MAX_PAGE_SIZE = 100;
const REQUEST_TIMEOUT_MS = 10_000;
```

Локальные неизменяемые значения, существующие только в пределах функции, могут использовать `camelCase`.

```ts
const normalizedStatus = status.trim().toUpperCase();
```

В JavaScript и TypeScript препроцессорные макросы обычно не используются. Под термином «макросы» в проекте понимаются:

- переменные окружения;
- параметры сборки;
- константы конфигурации;
- значения Docker Compose.

Имена переменных окружения задаются в `UPPER_SNAKE_CASE`:

```text
NODE_ENV
PORT
DATABASE_URL
LOG_LEVEL
CORS_ALLOWED_ORIGINS
API_BASE_URL
POSTGRES_DB
POSTGRES_USER
POSTGRES_PASSWORD
```

## 3.5. Имена типов, интерфейсов, классов и перечислений

Для типов, интерфейсов, классов и перечислений используется `PascalCase`.

```ts
interface CreateMeetingRequest {
  title: string;
}

type TaskStatusCode = 'NOT_STARTED' | 'IN_PROGRESS' | 'COMPLETED';

class ProtocolService {
  // ...
}

enum TaskStatus {
  NotStarted = 'NOT_STARTED',
  InProgress = 'IN_PROGRESS',
  Completed = 'COMPLETED',
}
```

Не следует добавлять префикс `I` к интерфейсам:

```ts
interface MeetingRepository {}   // правильно
interface IMeetingRepository {}  // не рекомендуется
```

DTO должны содержать назначение и направление передачи:

```ts
CreateMeetingRequestDto
UpdateTaskRequestDto
MeetingResponseDto
TaskListQueryDto
```

## 3.6. Имена REST API

URL REST API:

- используют множественное число;
- используют `kebab-case`;
- не содержат глаголов, если действие выражается HTTP-методом;
- начинаются с версии API.

```text
GET    /api/v1/meetings
POST   /api/v1/meetings
GET    /api/v1/meetings/{meetingId}
PATCH  /api/v1/meetings/{meetingId}
DELETE /api/v1/meetings/{meetingId}

GET    /api/v1/meetings/{meetingId}/protocol
POST   /api/v1/meetings/{meetingId}/protocol

GET    /api/v1/tasks
PATCH  /api/v1/tasks/{taskId}/status
```

Параметры JSON используют `camelCase`:

```json
{
  "plannedDueDate": "2026-08-03",
  "responsiblePersonId": "42"
}
```

Коды перечислений используют `UPPER_SNAKE_CASE`:

```json
{
  "status": "IN_PROGRESS"
}
```

## 3.7. Имена объектов PostgreSQL

Имена таблиц, столбцов, индексов и ограничений используют `snake_case`.

```text
meetings
meeting_participants
agenda_items
task_status_history

planned_due_date
actual_completion_date
responsible_person_id
```

Имена таблиц используются во множественном числе.

Имена внешних ключей заканчиваются на `_id`.

Имена индексов:

```text
idx_<table>_<columns>
```

Пример:

```text
idx_tasks_status
idx_tasks_responsible_person_id
```

Имена уникальных ограничений:

```text
uq_<table>_<columns>
```

Имена внешних ключей:

```text
fk_<table>_<referenced_table>
```

Имена проверочных ограничений:

```text
chk_<table>_<rule>
```

Пример:

```text
chk_tasks_progress_percent
```

# 4. Правила подключения библиотек

## 4.1. Общие требования

Перед добавлением библиотеки необходимо проверить:

- нельзя ли решить задачу стандартными средствами платформы;
- поддерживается ли библиотека;
- совместима ли лицензия библиотеки с проектом;
- отсутствуют ли известные критические уязвимости;
- не дублирует ли она уже подключённую зависимость;
- оправдан ли её размер и влияние на контейнерный образ;
- есть ли типы TypeScript или официальный пакет типов.

Каждая зависимость должна иметь конкретное назначение. Запрещено добавлять библиотеку «на будущее».

---

## 4.2. Декларирование зависимостей бэкенда

Все зависимости бэкенда объявляются в `backend/package.json`.

Зависимости времени выполнения размещаются в `dependencies`:

```json
{
  "dependencies": {
    "express": "5.1.0",
    "pg": "8.16.0"
  }
}
```

Инструменты разработки размещаются в `devDependencies`:

```json
{
  "devDependencies": {
    "@types/node": "24.0.0",
    "eslint": "9.0.0",
    "typescript": "5.8.0",
    "vitest": "3.0.0"
  }
}
```

Правила:

- файл блокировки `package-lock.json` обязателен и хранится в Git;
- в CI и Docker-сборке применяется `npm ci`, а не `npm install`;
- версии основных зависимостей должны быть зафиксированы;
- обновление зависимостей выполняется отдельным коммитом или отдельным pull request;
- после обновления выполняются тесты и аудит зависимостей;
- пакеты не импортируются через внутренние пути, не являющиеся публичным API библиотеки.

---

## 4.3. Порядок импортов TypeScript

Импорты группируются в следующем порядке:

1. встроенные модули Node.js;
2. внешние библиотеки;
3. внутренние абсолютные импорты;
4. относительные импорты текущего модуля;
5. импорты типов.

Между группами оставляется пустая строка.

```ts
import { randomUUID } from 'node:crypto';

import express from 'express';
import { z } from 'zod';

import { database } from '@/infrastructure/database/database-client.js';
import { logger } from '@/infrastructure/logging/logger.js';

import { mapTaskResponse } from './task-mapper.js';

import type { Request, Response } from 'express';
import type { TaskRepository } from './task-repository.js';
```

Требования:

- запрещён неиспользуемый импорт;
- звёздочный импорт применяется только при наличии обоснования;
- циклические зависимости между модулями запрещены;
- внутренние модули не должны импортироваться через длинные цепочки `../../../`.

---

## 4.4. Подключение библиотек во фронтенде

Поскольку фронтенд является одностраничным HTML-приложением, рекомендуется использовать ES-модули.

```html
<script type="module" src="./js/app.js"></script>
```

В JavaScript:

```js
import { apiClient } from './api/api-client.js';
import { renderMeetingList } from './features/meetings/meeting-list.js';
```

Рекомендуемый способ подключения внешней библиотеки:

1. установить её как зависимость фронтенда;
2. включить в процесс сборки или копирования статических ресурсов;
3. зафиксировать версию в `frontend/package.json` и `package-lock.json`.

Подключение библиотек напрямую с публичного CDN допускается только для прототипа. Для рабочего контура оно не рекомендуется по причинам:

- зависимости от внешней сети;
- невозможности гарантировать доступность;
- риска изменения содержимого;
- требований информационной безопасности.

Если CDN всё же применяется, версия должна быть зафиксирована, а тег должен содержать SRI-проверку `integrity`.

---

## 4.5. Подключение CSS

CSS подключается только через основной файл:

```html
<link rel="stylesheet" href="./css/main.css">
```

`main.css` может импортировать тематические файлы:

```css
@import url("./base/reset.css");
@import url("./base/variables.css");
@import url("./layout/page-layout.css");
@import url("./components/button.css");
@import url("./features/task-list.css");
```

Не допускаются:

- большие блоки CSS внутри HTML;
- стили через атрибут `style`, кроме динамически вычисляемых значений;
- дублирование переменных цветов и размеров;
- использование `!important` без документированного обоснования.

## 6.2. Правила фронтенда

- `index.html` содержит каркас приложения, но не бизнес-логику.
- Встроенные обработчики вида `onclick="..."` запрещены.
- Обработчики событий назначаются через `addEventListener`.
- Работа с REST API сосредоточена в каталоге `api/`.
- Функции формирования DOM не должны самостоятельно выполнять HTTP-запросы.
- Общие UI-компоненты размещаются в `components/`.
- Код конкретного бизнес-раздела размещается в `features/<feature-name>/`.
- Все запросы должны обрабатывать:
  - успешный ответ;
  - ошибку валидации;
  - отсутствие авторизации;
  - серверную ошибку;
  - сетевой тайм-аут.
- Пользовательские данные, вставляемые в DOM, должны экранироваться.
- `innerHTML` не используется для непроверенных данных.
- API URL берётся из runtime-конфигурации, а не записывается в каждом модуле.
- Состояние приложения не хранится в DOM как в единственном источнике истины.

Пример разделения ответственности:

```js
// api/task-api.js
export async function getTasks(filters) {
  return apiClient.get('/api/v1/tasks', filters);
}

// features/tasks/task-list.js
export async function loadTaskList() {
  const tasks = await getTasks(currentFilters);
  renderTaskList(tasks);
}
```

## 7.2. Разделение слоёв бэкенда

### Controller

Отвечает за:

- чтение параметров HTTP-запроса;
- вызов валидации;
- вызов сервиса;
- формирование HTTP-ответа.

Controller не должен содержать SQL и сложную бизнес-логику.

### Service

Отвечает за:

- бизнес-правила;
- проверку допустимости операций;
- координацию нескольких репозиториев;
- управление транзакцией;
- преобразование бизнес-ошибок.

Пример правила:

> Задача не может быть создана без решения и обсуждаемого вопроса.

### Repository

Отвечает за:

- чтение и запись данных;
- SQL или вызовы ORM;
- преобразование строк БД в внутренние структуры;
- отсутствие HTTP-зависимостей.

### Mapper

Отвечает за преобразование:

- записи БД в доменную модель;
- доменной модели в DTO ответа;
- входного DTO в структуру команды.

### Validation

Отвечает за проверку:

- обязательных полей;
- типов;
- форматов;
- диапазонов;
- допустимых значений перечислений.

## 7.3. Правила TypeScript

- Включается строгий режим: `"strict": true`.
- Тип `any` запрещён, кроме документированных интеграционных случаев.
- Для неизвестных данных используется `unknown` с последующей проверкой.
- Публичные функции должны иметь явный тип результата.
- Внешние данные не считаются типобезопасными до runtime-валидации.
- Не следует использовать `as` для подавления ошибок типов без обоснования.
- Ошибки должны передаваться через типизированные классы или коды.
- Асинхронные операции выполняются через `async/await`.
- Необработанные Promise запрещены.
- Для идентификаторов не выполняются арифметические операции.
- Денежные значения не хранятся в `number` без анализа точности.

Пример:

```ts
export async function getTaskById(taskId: string): Promise<TaskResponseDto> {
  const task = await taskRepository.findById(taskId);

  if (!task) {
    throw new NotFoundError('TASK_NOT_FOUND', 'Task was not found');
  }

  return mapTaskResponse(task);
}
```

# 8. Правила проектирования REST API

## 8.1. HTTP-методы

- `GET` — чтение;
- `POST` — создание;
- `PUT` — полная замена ресурса;
- `PATCH` — частичное изменение;
- `DELETE` — удаление.

Операция чтения не должна изменять состояние системы.

---

## 8.2. Коды ответов

- `200 OK` — успешное чтение или изменение;
- `201 Created` — ресурс создан;
- `204 No Content` — успешная операция без тела ответа;
- `400 Bad Request` — некорректный формат запроса;
- `401 Unauthorized` — пользователь не аутентифицирован;
- `403 Forbidden` — недостаточно прав;
- `404 Not Found` — ресурс не найден;
- `409 Conflict` — конфликт бизнес-состояния;
- `422 Unprocessable Entity` — ошибка проверки данных;
- `500 Internal Server Error` — непредвиденная ошибка.

---

## 8.3. Формат ошибки

Все ошибки REST API используют единый формат:

```json
{
  "error": {
    "code": "TASK_STATUS_TRANSITION_NOT_ALLOWED",
    "message": "Task cannot be moved from COMPLETED to IN_PROGRESS",
    "details": {
      "currentStatus": "COMPLETED",
      "requestedStatus": "IN_PROGRESS"
    },
    "requestId": "6a33b7aa-8fbe-4e25-95a5-8d3ed97f5f79"
  }
}
```

Пользователю не возвращаются:

- stack trace;
- SQL;
- пароль;
- строка подключения;
- внутренний путь к файлу;
- содержимое переменных окружения.

---

## 8.4. Пагинация и фильтрация

Списочные методы должны поддерживать пагинацию.

```text
GET /api/v1/tasks?page=1&pageSize=25&status=IN_PROGRESS
```

Рекомендуемый ответ:

```json
{
  "items": [],
  "pagination": {
    "page": 1,
    "pageSize": 25,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

Максимальный размер страницы задаётся константой на бэкенде.

# 9. Работа с PostgreSQL

## 9.1. Общие правила

- Все таблицы имеют первичный ключ.
- Все связи оформляются внешними ключами.
- Обязательность данных обеспечивается `NOT NULL`.
- Уникальность бизнес-идентификаторов обеспечивается `UNIQUE`.
- Инварианты, которые можно гарантировать в БД, должны быть оформлены ограничениями.
- SQL-запросы всегда параметризуются.
- Конкатенация пользовательских значений в SQL запрещена.
- Операции, изменяющие несколько связанных сущностей, выполняются в транзакции.
- Время хранится в `timestamptz`, если момент зависит от часового пояса.
- Даты без времени хранятся в `date`.
- Статусы не хранятся в свободном тексте.
- Для удаления значимых данных предпочтительно логическое удаление или архивирование.
- Внешние ключи и условия частых выборок должны иметь индексы.

---

## 9.2. Миграции

```text
database/
├── migrations/
│   ├── 0001-initial-schema.sql
│   ├── 0002-add-task-history.sql
│   └── 0003-add-protocol-approval.sql
├── seeds/
│   ├── development.sql
│   └── test.sql
└── schema/
    └── meeting-protocol.dbml
```

Правила:

- уже применённая миграция не изменяется;
- исправление выполняется новой миграцией;
- имя миграции описывает изменение;
- миграция должна иметь понятный путь отката либо документированную необратимость;
- тестовые данные не включаются в production-миграцию;
- изменение схемы и соответствующее изменение кода выполняются согласованно.

---

## 9.3. Транзакции

Транзакция обязательна, например, при:

- создании протокола вместе с обсуждениями;
- создании решения и связанных задач;
- изменении статуса задачи с записью истории;
- переносе срока задачи с записью причины;
- удалении или архивировании совещания с зависимыми сущностями.

Транзакции должны быть короткими. Внутри транзакции не выполняются внешние HTTP-запросы.

# 10. Контейнерная архитектура

## 10.1. Контейнеры

Проект содержит как минимум три сервиса:

```text
frontend
backend
database
```

Назначение:

- `frontend` — выдаёт статические HTML, CSS и JavaScript;
- `backend` — предоставляет REST API;
- `database` — запускает PostgreSQL.

---

## 10.2. Правила Docker

- Каждый сервис имеет собственный `Dockerfile`.
- Контейнер выполняет один основной процесс.
- Для production используются минимальные базовые образы.
- Бэкенд собирается через multi-stage build.
- В production-образ не копируются тесты, исходники и dev-зависимости, если они не нужны.
- Контейнеры не запускаются от `root`, если это технически возможно.
- В образы не копируется `.env`.
- Конфигурация передаётся переменными окружения.
- Данные PostgreSQL хранятся в именованном volume.
- Для сервисов задаются `healthcheck`.
- Бэкенд должен ожидать готовности БД на уровне повторных попыток подключения, а не только порядка запуска.
- Внутри Docker-сети сервисы обращаются друг к другу по имени сервиса.
- Бэкенд не публикует порт БД наружу без необходимости.
- REST API не должен использовать `localhost` для обращения к другому контейнеру.

Пример адресов внутри сети Compose:

```text
postgresql://app_user:password@database:5432/meeting_protocol
http://backend:3000
```

Браузер пользователя не видит внутреннее имя `backend`. Для фронтенда рекомендуется проксировать `/api` через веб-сервер фронтенд-контейнера:

```text
Browser -> frontend:80/api -> backend:3000
```

Это упрощает CORS и конфигурацию URL.

---

## 10.3. Docker Compose

`docker-compose.yml` должен:

- определять отдельные сервисы;
- использовать переменные из `.env`;
- содержать именованные сети и volumes;
- не содержать реальных production-секретов;
- задавать зависимости и healthcheck;
- предоставлять понятные имена контейнеров или сервисов.

Файл `.env.example` содержит только пример:

```text
POSTGRES_DB=meeting_protocol
POSTGRES_USER=meeting_app
POSTGRES_PASSWORD=change-me
BACKEND_PORT=3000
FRONTEND_PORT=8080
LOG_LEVEL=debug
```

# 11. Вывод отладочной информации и журналирование

## 11.1. Общие правила

Отладочная информация должна:

- иметь уровень важности;
- содержать время;
- содержать название сервиса;
- содержать идентификатор запроса;
- быть пригодной для поиска;
- не раскрывать секреты и персональные данные сверх необходимого;
- выводиться в `stdout` и `stderr`, чтобы Docker мог собирать логи.

Запрещено использовать отладочные сообщения как механизм бизнес-учёта.

---

## 11.2. Уровни журналирования

Используются уровни:

- `trace` — детальный ход выполнения;
- `debug` — информация для разработки;
- `info` — штатные значимые события;
- `warn` — отклонение, не остановившее операцию;
- `error` — ошибка операции;
- `fatal` — невозможность продолжить работу процесса.

В production обычно используются `info`, `warn`, `error`, `fatal`.

Уровень задаётся через:

```text
LOG_LEVEL=info
```

---

## 11.3. Логирование бэкенда

На бэкенде используется единый модуль logger. Прямое применение `console.log` в прикладном коде запрещается.

Допустимо использовать `console` только:

- до инициализации logger;
- в минимальном bootstrap-коде;
- в одноразовом локальном диагностическом скрипте.

Рекомендуется структурированный JSON-лог:

```json
{
  "level": "info",
  "time": "2026-07-21T18:10:00.000Z",
  "service": "meeting-protocol-backend",
  "requestId": "6a33b7aa-8fbe-4e25-95a5-8d3ed97f5f79",
  "method": "PATCH",
  "path": "/api/v1/tasks/03-001/status",
  "event": "task_status_changed",
  "taskCode": "03-001",
  "previousStatus": "NOT_STARTED",
  "newStatus": "IN_PROGRESS"
}
```

Ошибки логируются с техническими подробностями на сервере:

```ts
logger.error(
  {
    err: error,
    requestId,
    taskId,
  },
  'Failed to update task status',
);
```

Не логируются:

- пароли;
- токены;
- cookie авторизации;
- `Authorization` header;
- полные строки подключения;
- содержимое документов без необходимости;
- полный объект request;
- персональные сведения, не требуемые для диагностики.

---

## 11.4. Идентификатор запроса

Каждый HTTP-запрос получает `requestId`.

- Если клиент передал допустимый `X-Request-Id`, он может быть принят.
- Иначе бэкенд генерирует UUID.
- `requestId` добавляется в ответ.
- Все логи обработки запроса содержат одинаковый `requestId`.

Это позволяет связать ошибку фронтенда, HTTP-запрос и серверные логи.

---

## 11.5. Отладка фронтенда

Во фронтенде должен использоваться единый модуль:

```text
src/js/shared/logger.js
```

Пример интерфейса:

```js
logger.debug('Task list loaded', { itemCount: tasks.length });
logger.warn('Task has no planned due date', { taskId });
logger.error('Failed to load protocol', { error, requestId });
```

`console.debug` и подробные сообщения отключаются в production-конфигурации.

В UI пользователю показывается краткое сообщение:

```text
Не удалось загрузить протокол. Код запроса: 6a33b7aa...
```

Техническая причина остаётся в консоли разработчика и серверных логах.

---

## 11.6. Отладка контейнеров

Основные команды:

```bash
docker compose ps
docker compose logs frontend
docker compose logs backend
docker compose logs database
docker compose logs -f backend
docker compose exec backend sh
docker compose exec database psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Контейнеры не должны записывать единственную копию логов во внутренний файл контейнера. Если файловый лог необходим, каталог должен быть подключён как volume и настроена ротация.

---

## 11.7. Отладка SQL

Для диагностики запросов допускается логировать:

- имя операции;
- длительность;
- число возвращённых строк;
- идентификатор транзакции;
- код ошибки PostgreSQL.

Не следует логировать значения всех параметров запроса по умолчанию.

Медленные запросы должны фиксироваться при превышении заданного порога:

```text
DB_SLOW_QUERY_MS=500
```

Для анализа применяются:

```sql
EXPLAIN;
EXPLAIN ANALYZE;
```

`EXPLAIN ANALYZE` на production выполняется только с пониманием того, что запрос будет реально исполнен.

# 12. Обработка ошибок

- Ошибка не должна подавляться пустым `catch`.
- Любая перехваченная ошибка должна быть:
  - обработана;
  - преобразована в доменную ошибку;
  - либо повторно выброшена.
- Не следует использовать исключения для обычного ветвления.
- Ошибки инфраструктуры не должны напрямую становиться текстом ответа.
- Для ожидаемых ошибок используются стабильные машинные коды.

Пример:

```ts
try {
  await taskRepository.updateStatus(taskId, newStatus);
} catch (error: unknown) {
  logger.error({ err: error, taskId }, 'Database operation failed');
  throw new InfrastructureError('TASK_UPDATE_FAILED');
}
```

# 14. Комментарии и документация

Комментарии объясняют причину решения, а не повторяют код.

Нежелательно:

```ts
// Set status to completed
task.status = TaskStatus.Completed;
```

Предпочтительно:

```ts
// Completion date is persisted together with the status
// to preserve the task lifecycle invariant.
task.status = TaskStatus.Completed;
```

Публичные функции и сложные бизнес-правила документируются через TSDoc.

Необходимо документировать:

- нестандартные решения;
- временные обходные механизмы;
- ограничения PostgreSQL;
- причины использования raw SQL;
- ручные шаги миграции;
- формат интеграционного API.

Метки `TODO` должны содержать причину или ссылку на задачу:

```ts
// TODO(MPS-142): replace polling with server-sent events.
```

# 15. Безопасность

- Все внешние данные валидируются.
- SQL-запросы параметризуются.
- HTML-данные экранируются.
- CORS ограничивается известными origin.
- Размер тела HTTP-запроса ограничивается.
- Файловые пути и имена вложений проверяются.
- Секреты поступают только из безопасной конфигурации.
- Пароли не хранятся в открытом виде.
- Для production используется HTTPS.
- Контейнерные образы регулярно пересобираются и проверяются.
- Зависимости проверяются на известные уязвимости.
- Ошибки не раскрывают внутреннюю структуру системы.

# 16. Тестирование

Минимально предусматриваются:

- unit-тесты бизнес-логики;
- integration-тесты репозиториев с PostgreSQL;
- API-тесты основных REST endpoint;
- тесты миграций;
- smoke-тест запуска Docker Compose;
- ручная или автоматизированная проверка основных сценариев фронтенда.

Критические сценарии:

- создание единственного протокола совещания;
- добавление информационного обсуждения без решения;
- добавление обсуждения с решением;
- создание задачи, связанной с обсуждением и решением;
- изменение статуса задачи;
- сохранение фактической даты завершения;
- контроль задачи на последующем совещании;
- запрет недопустимого перехода статуса.

Тесты не должны зависеть от порядка запуска и общих изменяемых данных.

# 17. Git и изменения кода

- Одна ветка должна решать одну задачу.
- Коммит должен быть логически целостным.
- Изменение схемы БД сопровождается миграцией.
- Изменение API сопровождается обновлением документации и тестов.
- Сгенерированные артефакты не добавляются в Git, если это не требуется процессом поставки.
- `.env`, дампы БД, журналы и секреты не коммитятся.
- Перед pull request выполняются все локальные проверки.
- Pull request должен описывать:
  - что изменено;
  - зачем;
  - как проверить;
  - меняется ли API;
  - меняется ли схема БД;
  - требуются ли новые переменные окружения.

---

# 18. Критерии готовности изменения

Изменение считается готовым, если:

- код соответствует соглашениям об именовании;
- структура файлов не нарушена;
- зависимости корректно объявлены;
- отсутствуют секреты;
- TypeScript компилируется без ошибок;
- линтер и formatter проходят;
- тесты проходят;
- миграции применяются на чистой БД;
- Docker-образы собираются;
- Docker Compose запускает три сервиса;
- frontend обращается к backend только через REST API;
- ошибки и отладочная информация выводятся через установленный механизм;
- документация обновлена;
- новые endpoint и переменные окружения описаны.

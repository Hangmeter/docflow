# Спецификация требований на разработку системы ведения протоколов совещаний

## 1. Назначение документа

Документ определяет требования к разработке веб-системы ведения протоколов совещаний и предназначен для передачи в работу Codex.

Codex должен использовать:

- настоящую спецификацию как основной источник функциональных требований;
- `dev-guide.md` как обязательный источник правил разработки;
- DBML-модель проекта как источник структуры данных;
- миграции PostgreSQL как единственный способ изменения схемы базы данных.

При противоречии документов приоритет имеет следующая последовательность:

1. настоящая спецификация;
2. DBML-модель;
3. `dev-guide.md`;
4. существующий исходный код;
5. комментарии в коде.

Codex не должен самостоятельно изменять предметную область или добавлять функции, не предусмотренные спецификацией, без явного задания.

---

# 2. Цель системы

Система предназначена для:

- регистрации совещаний;
- ведения единственного протокола каждого совещания;
- формирования повестки;
- регистрации участников и их присутствия;
- фиксации хода обсуждения вопросов;
- регистрации принятых решений;
- назначения задач по результатам решений;
- контроля сроков и статусов задач;
- рассмотрения ранее назначенных задач на последующих совещаниях;
- поиска и просмотра истории совещаний, решений и задач.

Система должна заменить ведение протоколов в неструктурированных Markdown-, Word- и табличных документах структурированным хранением данных в PostgreSQL.

# 3. Границы первой версии

## 3.1. В MVP входят

1. Справочник сотрудников.
2. Справочник организаций и подразделений.
3. Создание, просмотр и редактирование совещаний.
4. Создание одного протокола для каждого совещания.
5. Управление повесткой совещания.
6. Управление участниками и отметками присутствия.
7. Фиксация обсуждений.
8. Фиксация информационных обсуждений без решений.
9. Фиксация решений.
10. Назначение задач по решениям.
11. Изменение статуса и сроков задач.
12. Просмотр списка задач.
13. Контроль задач на последующих совещаниях.
14. Просмотр сводной таблицы решений и поручений.
15. Журналирование основных операций.
16. Запуск фронтенда, бэкенда и PostgreSQL в отдельных контейнерах.

## 3.2. В MVP не входят

- интеграция с электронной почтой;
- интеграция с календарями;
- автоматическая расшифровка аудио и видео;

- полнотекстовый поиск по вложениям;
- сложная ролевая модель доступа;

- уведомления исполнителей;
- синхронизация с внешними кадровыми системами;
- графовая аналитика;
- мобильное приложение;
- совместное редактирование в реальном времени.

Архитектура не должна препятствовать добавлению этих функций позднее.

# 4. Технологические требования

## 4.1. Фронтенд

Фронтенд должен быть одностраничным приложением:

- один основной `index.html`;
- JavaScript в виде ES modules;
- CSS без серверного рендеринга;
- без обязательного использования React, Vue, Angular или другого SPA-фреймворка;
- взаимодействие с бэкендом только через REST API;
- выдача статических файлов через отдельный контейнер с Nginx.

Допускается минимальный инструмент сборки, если он нужен для линтинга, тестирования или управления зависимостями. Итоговый фронтенд должен оставаться набором статических файлов.

## 4.2. Бэкенд

Бэкенд:

- Node.js;
- TypeScript;
- REST API;
- строгий режим TypeScript;
- валидация всех входных данных;
- параметризованные запросы к PostgreSQL;
- структурированное журналирование;
- единый обработчик ошибок.

Предпочтительный HTTP-фреймворк: Express.

Предпочтительный доступ к БД для MVP: `pg` с отдельным repository-слоем. Использование Prisma допускается только при сохранении всех ограничений БД в SQL-миграциях и без изменения утверждённой модели.

## 4.3. База данных

- PostgreSQL;
- кодировка UTF-8;
- хранение всех данных в отдельном контейнере;
- изменение схемы только миграциями;
- тестовые данные — отдельными seed-скриптами;
- сохранение данных через named volume.

## 4.4. Контейнеры

Минимальный набор сервисов Docker Compose:

```text
frontend
backend
database
```

Требования:

- каждый сервис имеет собственный Dockerfile;
- бэкенд не хранит состояние в файловой системе контейнера;
- frontend проксирует `/api/` на backend;
- PostgreSQL доступен backend по имени сервиса `database`;
- должны быть healthcheck;
- должны использоваться переменные окружения;
- секреты не включаются в Git.

# 5. Пользовательские роли MVP

В MVP достаточно двух прикладных ролей.

## 5.1. Секретарь

Может:

- создавать и редактировать совещания;
- создавать и редактировать протокол;
- управлять повесткой;
- управлять списком участников;
- фиксировать обсуждения;
- добавлять решения;
- создавать задачи;
- изменять сроки и статусы задач;
- добавлять результаты контроля задач.

## 5.2. Наблюдатель

Может:

- просматривать совещания;
- просматривать протоколы;
- просматривать решения;
- просматривать задачи.

Полноценная аутентификация не входит в MVP. Для разработки допускается выбор текущей роли через конфигурацию или временный заголовок. При этом проверки прав должны быть сосредоточены на бэкенде, чтобы позднее можно было заменить механизм аутентификации.

# 6. Основные сущности предметной области

## 6.1. Совещание

Содержит:

- внутренний ID;
- номер;
- название;
- тип;
- формат;
- плановое время начала и окончания;
- фактическое время начала и окончания;
- место;
- ссылку на ВКС;
- дату следующего совещания;
- особые отметки.

Правило:

> Каждое совещание должно иметь не более одного протокола. Для завершённого совещания протокол обязателен.

## 6.2. Протокол

Содержит:

- внутренний ID;
- номер;
- дату;
- статус;
- ссылку на совещание;
- вводную и заключительную части;
- сведения об утверждении.

Статусы:

- `DRAFT`;
- `ON_APPROVAL`;
- `APPROVED`;
- `ARCHIVED`;
- `CANCELLED`.

## 6.3. Пункт повестки

Содержит:

- номер вида `1`, `1.1`, `2.3`;
- название;
- описание;
- порядок отображения;
- родительский пункт.

Поддерживается иерархия минимум в два уровня.

## 6.4. Обсуждение

Обсуждение связано:

- с протоколом;
- с пунктом повестки;
- с одним или несколькими выступающими.

Содержит:

- тему;
- текст обсуждения;
- тип результата;
- порядок следования.

Тип результата:

- `INFORMATION_ONLY`;
- `DECISION_MADE`;
- `POSTPONED`;
- `NO_DECISION`.

Информационное обсуждение может не иметь решений и задач.

## 6.5. Решение

Решение:

- обязательно связано с обсуждением;
- содержит номер внутри обсуждения;
- содержит текст;
- имеет статус;
- может не порождать задач;
- может порождать одну или несколько задач.

## 6.6. Задача

Задача обязательно связана:

- с обсуждением;
- с решением;
- с ответственным сотрудником.

Содержит:

- уникальный код;
- название;
- описание;
- ответственного;
- при необходимости соисполнителей;
- статус;
- приоритет;
- дату назначения;
- плановый срок;
- исходную текстовую формулировку срока;
- фактическую дату начала;
- фактическую дату завершения;
- процент выполнения;
- результат;
- комментарий.

Статусы:

- `NOT_STARTED`;
- `IN_PROGRESS`;
- `BLOCKED`;
- `ON_HOLD`;
- `COMPLETED`;
- `CANCELLED`;
- `OVERDUE`.

## 6.7. Контроль задачи

Одна задача может рассматриваться на нескольких последующих совещаниях.

Запись контроля должна хранить снимок:

- совещание, на котором задача рассмотрена;
- статус на момент рассмотрения;
- плановый срок;
- фактическую дату завершения;
- результат рассмотрения;
- комментарий;
- дату и автора проверки.

# 7. Бизнес-правила

## 7.1. Совещания и протоколы

1. У одного совещания не может быть более одного протокола.
2. Протокол нельзя создать без совещания.
3. Номер протокола должен быть уникальным.
4. Утверждённый протокол нельзя изменять обычной операцией редактирования.
5. Для изменения утверждённого протокола требуется вернуть его в статус `DRAFT` или создать механизм исправления в будущей версии.
6. Удаление совещания с протоколом в MVP запрещено; допускается архивирование.

## 7.2. Обсуждения и решения

1. Обсуждение обязательно связано с пунктом повестки.
2. `INFORMATION_ONLY` не требует решения.
3. Для `DECISION_MADE` должно существовать не менее одного решения.
4. Решение не существует вне обсуждения.
5. Нумерация решений уникальна внутри обсуждения.

## 7.3. Задачи

1. Задачу нельзя создать без решения.
2. Решение и обсуждение задачи должны принадлежать одной цепочке.
3. Код задачи уникален.
4. Ответственный обязателен.
5. Процент выполнения находится в диапазоне 0–100.
6. Для статуса `COMPLETED`:
   - процент выполнения равен 100;
   - фактическая дата завершения обязательна.
7. При изменении статуса создаётся запись в истории.
8. При изменении планового срока создаётся запись в истории сроков.
9. Если плановая дата прошла, а задача не завершена и не отменена, задача считается просроченной.
10. Неформализованный срок, например «после 27.07.2026», хранится в отдельном текстовом поле. Если возможно выделить точную дату, она сохраняется дополнительно.
11. Контроль задачи на совещании не должен изменять исторический снимок контроля после утверждения протокола.

## 7.4. Участники

1. Один сотрудник не должен дважды добавляться в одно совещание с одной ролью.
2. Председатель и секретарь должны быть зарегистрированы как участники совещания.
3. Должность, подразделение и организация сохраняются в участнике совещания как снимок на момент совещания.

# 8. Функциональные требования

## FR-01. Список совещаний

Система должна отображать список совещаний.

Колонки:

- номер;
- название;
- дата и время;
- тип;
- формат;
- статус протокола;
- председатель;
- количество открытых задач.

Функции:

- пагинация;
- сортировка по дате;
- фильтр по диапазону дат;
- фильтр по типу;
- фильтр по статусу протокола;
- текстовый поиск по номеру и названию;
- переход в карточку совещания;
- создание нового совещания.

## FR-02. Карточка совещания

Карточка должна содержать разделы:

1. Основные сведения.
2. Участники.
3. Повестка.
4. Протокол.
5. Решения и задачи.
6. Контроль ранее назначенных задач.

Должны поддерживаться создание и редактирование полей совещания.

## FR-03. Участники совещания

Пользователь должен иметь возможность:

- добавить сотрудника;
- выбрать роль;
- отметить присутствие;
- удалить участника до утверждения протокола;
- видеть должность и подразделение;
- назначить председателя;
- назначить секретаря.

## FR-04. Повестка

Пользователь должен иметь возможность:

- добавить раздел;
- добавить подпункт;
- изменить номер и название;
- изменить порядок;
- удалить пустой пункт;
- открыть обсуждение по пункту.

Порядок должен сохраняться явно, а не вычисляться только по номеру.

## FR-05. Ведение обсуждения

Для пункта повестки пользователь должен иметь возможность:

- указать тему;
- указать выступающих;
- ввести текст обсуждения;
- выбрать тип результата;
- добавить ссылки и материалы;
- добавить решения;
- сохранить обсуждение без решения.

## FR-06. Решения

Пользователь должен иметь возможность:

- добавить несколько решений к обсуждению;
- изменить текст решения;
- отменить решение;
- создавать задачи по решению;
- просматривать задачи решения.

## FR-07. Создание задачи

Форма задачи должна содержать:

- код задачи;
- название;
- описание;
- ответственного;
- соисполнителей;
- приоритет;
- плановую дату;
- текстовую формулировку срока;
- комментарий.

При создании задачи значения:

- статус — `NOT_STARTED`;
- процент выполнения — `0`;
- дата назначения — текущая дата и время.

## FR-08. Список задач

Колонки:

- код;
- название;
- совещание;
- обсуждаемый вопрос;
- решение;
- ответственный;
- статус;
- приоритет;
- плановая дата;
- фактическая дата;
- процент выполнения.

Фильтры:

- статус;
- ответственный;
- совещание;
- диапазон плановых дат;
- просроченные;
- поиск по коду и названию.

## FR-09. Карточка задачи

Должна отображать:

- основные поля;
- источник задачи;
- историю статусов;
- историю сроков;
- совещания, на которых задача контролировалась;
- ссылки и материалы.

Должны поддерживаться:

- изменение статуса;
- изменение процента;
- изменение срока с обязательным указанием причины;
- завершение задачи;
- добавление комментария;
- добавление результата выполнения.

## FR-10. Контроль задач

В карточке совещания пользователь должен иметь возможность:

- выбрать незавершённые задачи предыдущих совещаний;
- добавить их в раздел контроля;
- зафиксировать статус;
- зафиксировать комментарий;
- принять результат;
- вернуть на доработку;
- продлить срок;
- отменить задачу.

## FR-11. Сводная таблица решений и поручений

Для протокола должна автоматически формироваться таблица:

- номер;
- обсуждённый вопрос;
- принятое решение;
- код задачи;
- ответственный;
- срок;
- статус.

Таблица является представлением данных и не хранится как отдельный вручную редактируемый набор строк.

## FR-12. Просмотр протокола

Система должна предоставлять режим просмотра протокола, близкий к печатному представлению:

- реквизиты совещания;
- повестка;
- присутствующие;
- ход совещания;
- решения;
- задачи;
- контроль поручений;
- заключительная часть.

В MVP достаточно HTML-представления и печати средствами браузера.

# 10. REST API

Базовый путь:

```text
/api/v1
```

Формат:

```text
Content-Type: application/json
```

## 10.1. Совещания

```text
GET    /meetings
POST   /meetings
GET    /meetings/{meetingId}
PATCH  /meetings/{meetingId}
POST   /meetings/{meetingId}/archive
```

Пример создания:

```json
{
  "meetingNumber": "4",
  "title": "Рабочее совещание по проекту",
  "meetingType": "PLANNED",
  "meetingFormat": "VIDEO_CONFERENCE",
  "scheduledStartAt": "2026-07-27T13:00:00+03:00",
  "scheduledEndAt": "2026-07-27T14:00:00+03:00",
  "location": "ВКС",
  "conferenceUrl": "https://example.test/conference"
}
```

## 10.2. Участники

```text
GET    /meetings/{meetingId}/participants
POST   /meetings/{meetingId}/participants
PATCH  /meetings/{meetingId}/participants/{participantId}
DELETE /meetings/{meetingId}/participants/{participantId}
```

## 10.3. Повестка

```text
GET    /meetings/{meetingId}/agenda-items
```

# 14. Нефункциональные требования

## NFR-01. Производительность

Для локального стенда при объёме:

- 10 000 совещаний;
- 100 000 обсуждений;
- 200 000 решений;
- 500 000 задач;

целевые значения:

- открытие списка — до 2 секунд;
- получение карточки — до 1 секунды;
- сохранение простой формы — до 1 секунды;
- фильтрация задач — до 2 секунд.

Значения измеряются без учёта медленной внешней сети.

## NFR-02. Надёжность

- операции над несколькими таблицами выполняются транзакционно;
- ошибка не должна оставлять частично созданную цепочку;
- backend должен корректно обрабатывать недоступность БД;
- контейнер должен завершаться с ненулевым кодом при невозможности старта;
- должен быть graceful shutdown.

## NFR-03. Безопасность

- параметризованные SQL-запросы;
- проверка тела, query и path параметров;
- ограничение размера запроса;
- защита от XSS;
- запрет выдачи stack trace клиенту;
- CORS по конфигурации;
- секреты только через переменные окружения;
- контейнер backend не должен запускаться от root;
- персональные данные не должны полностью попадать в debug-логи.

## NFR-04. Сопровождаемость

- модульная структура;
- единые DTO;
- отсутствие SQL в controllers;
- отсутствие HTTP-зависимостей в repositories;
- комментарии только для неочевидных решений;
- линтер и formatter;
- автоматические тесты;
- документированная конфигурация.

## NFR-05. Наблюдаемость

Backend должен предоставлять:

```text
GET /health
GET /ready
```

`/health` подтверждает работу процесса.

`/ready` подтверждает доступность PostgreSQL и готовность принимать запросы.

Логи выводятся в stdout/stderr в структурированном формате.

# 20. Критерии приёмки MVP

MVP принимается, если одновременно выполнены условия:

1. Репозиторий запускается через Docker Compose.
2. Запускаются три отдельных контейнера.
3. PostgreSQL сохраняет данные после перезапуска.
4. Frontend не обращается к БД напрямую.
5. Frontend использует REST API.
6. Можно создать совещание.
7. Можно создать один протокол.
8. Нельзя создать второй протокол.
9. Можно создать повестку.
10. Можно создать информационное обсуждение без решения.
11. Можно создать обсуждение с решением.
12. Можно создать задачу по решению.
13. Нельзя создать задачу без решения.
14. У задачи есть код, ответственный, срок, статус и фактическая дата завершения.
15. Статус задачи изменяется с записью истории.
16. Срок изменяется с записью причины и истории.
17. Завершённая задача имеет 100% и дату завершения.
18. Задача отображается в контроле последующего совещания.
19. Формируется сводная таблица решений и поручений.
20. API возвращает единый формат ошибок.
21. Логи backend содержат request ID.
22. Миграции применяются на чистой БД.
23. Seed создаёт демонстрационные данные.
24. Тесты проходят.
25. README содержит рабочие команды запуска.
